Browser Table Internals Deep Dive

Building the best table library requires understanding browser rendering. Most "10K row problems" are myths. Real optimization opportunities hide in layout algorithms.

The Three-Pass Layout Algorithm

HTML tables use a three-pass algorithm fundamentally different from div-based grids:

Pass 1: Intrinsic Sizing (Content-based width)

▼

Browser traverses every cell, calculates minimum width needed without wrapping. For 1000 cells, expensive. Optimization: CSS table-layout: fixed skips this entirely.

Pass 2: Preferred Sizing (Max available width)

▼

If content wraps, recalculate widths. @tablecraft uses CSS Grid, which skips passes 1–2 entirely. Pure CSS containment from start.

Pass 3: Final Distribution (Actual layout)

▼

Distribute space among columns. CSS Grid's fr units achieve this in O(1) time. Table algorithm is O(n²) worst case.

Layout Performance Comparison

Property table-layout: auto table-layout: fixed CSS Grid
Passes 3 2 1
Layout time (1K rows) 45–80ms 25–45ms 8–15ms
Reflow on content change Re-run all 3 Skip pass 1 No reflow (unless width changes)

Memory Overhead: The Hidden Crisis

HTML creates DOM nodes at ~100x HTML size multiplier:

Scenario HTML Size DOM Memory Multiplier
10 rows × 10 cols 5 KB 500 KB 100x
100 rows × 10 cols 50 KB 5 MB 100x
1,000 rows × 10 cols 500 KB 50 MB 100x
10,000 rows × 10 cols 5 MB 500 MB 100x

@tablecraft solution: Virtual scrolling keeps only 50 rows in DOM. 10,000 rows = 500 rows in DOM + data structure = ~5–10 MB total, not 500 MB.

Exploitable Optimizations

content-visibility (7x speedup)

▼ 
.table-row {
    content-visibility: auto;
    contain-intrinsic-size: 0 48px;
}

Browser skips layout for off-screen rows. Result: 10,000 rows render in 150ms instead of 1.5s.

CSS Containment (50–70% reduction)

▼ 
.table-row { contain: layout style paint; }

Changes to row don't affect others. Browser parallelizes layout. Massive perf win for large tables.

DOM Recycling (Zero allocations per scroll)

▼

Virtual scrolling doesn't throw away nodes. Updates them and reinserts. Garbage collection pressure reduced 90%+.

TanStack Table: The Headless Philosopher (7.9M weekly downloads, $0)

The Headless Thesis

▼

Tanner Linsley's positioning: "The headless table library." Core insight: tables are data management + UI. Separate them, developers ship their own UI and own the styling completely.

What makes this work:

  • No opinion on UI. Developers use Tailwind, shadcn/ui, or custom CSS.
  • Tiny core library. 45KB for all framework adapters.
  • Personal brand trust. Tanner has 200K+ Twitter followers. Community sees him as innovator.
  • Ecosystem lock. TanStack has Query, Router, Form, Start. Using one makes others natural.

Where TanStack is Vulnerable

▼
  • Boilerplate burden: "Headless" means you ship UI. That's 50–200 lines of code per table. Small startups don't have time.
  • Documentation for whom? API-heavy. Copy-paste examples exist, but core patterns require thinking.
  • No virtualization: Headless means scrolling optimization is your problem. Most choose pagination (worse UX).
  • Style inconsistency: Every team's table looks different. No design language. Feels chaotic at scale.
  • Mobile confusion: Headless doesn't tell you how to handle mobile. You invent it.
  • AI gap: Natural language, anomaly detection don't exist. Hard to retrofit into headless.

Mobile & Small Screens

The dimensional mismatch problem: 2D data in 1D scroll. Notion, Airtable, Linear all took different approaches. All have tradeoffs.

6 Patterns Tried (What we learned)

  • Responsive hiding: Hide columns on mobile. Problem: Lost context.
  • Horizontal scroll: Column scroll on mobile. Problem: Confusing on touch.
  • Cards: One row = one card. Problem: Slow to scan 1000 cards.
  • Master-detail: List + detail pane. Problem: Context switching fatigue.
  • Accordion: Expand rows. Problem: Data density lost.
  • Priority-based: Show key columns, inline others. Problem: Developers must configure.

5 Principles for Mobile-First Tables

  • Context-aware views: Show what matters for current task. Hide rest.
  • Touch-first interaction: No hover states. Tap to expand. Swipe to reveal.
  • Progressive disclosure: 2 columns visible, tap to reveal more.
  • Voice-enabled: "Show me rows where price > 100." Natural language queries.
  • Adaptive density: Compact on mobile, spacious on desktop.

Touch Gesture Vocabulary

  • Tap: Select, expand row, open edit mode
  • Long-press: Activate multi-select mode
  • Swipe left: Reveal right-pinned columns
  • Swipe right: Reveal left-pinned columns
  • Pinch: Adjust density (experimental)
  • Two-finger tap: Context menu (right-click equivalent)

Language & Architecture Decision

Why Svelte 5 for @tablecraft (not React, Vue, or Rust → WASM).

Language Options Evaluated

Language Advantages Disadvantages Verdict
Pure JS/TS Universal. No build step needed. Fastest dev cycle. Reactive state = manual tracking. Boilerplate heavy. Good for libraries, not frameworks
Svelte 5 Compiled reactivity. 30% faster load. 1.6KB runtime. Fine-grained updates. Runes syntax. Smaller ecosystem. Less Stack Overflow answers. ✓ CHOSEN. Best for paradigm shift product.
React Largest ecosystem. Job market. 18.2M weekly downloads. Virtual DOM overhead. 40KB min runtime. Slow renders at scale. Market standard, not performance standard
Vue Good DX. Smaller than React. Progressive enhancement. Smaller market. Less funding for innovation. Solid choice, but Svelte more differentiated
Rust → WASM 2–5x faster CPU. Predictable performance. No GC pauses. Slow start (100ms+ load time). Boundary tax. Complex build. Good for v2.5. Not v1 (premature optimization)
C++ → WASM Figma uses this. Proven at scale. Overkill for DOM tables. File parsing ≠ layout. Wrong problem domain. Wrong tool for job

Hybrid Optimal Approach

Svelte 5 + JS for rendering + WASM for 50K+ analytics.

  • v1 (now): Pure Svelte 5. 8KB minified. Ship fast, iterate.
  • v1.5: Optional WASM sort/filter for 50K+ row datasets.
  • v2.0: DuckDB-WASM integration. SQL queries in browser.
  • v2.5: Full WASM analytics engine. Perspective-like capabilities.

Verdict: Svelte 5 is Right

Paradigm shifts start with shipping fast, not shipping perfect. Svelte 5's compiled reactivity beats React's Virtual DOM. 1.6KB runtime beats Vue's. We can always add WASM later. Today, developer experience matters more than CPU cycles.
